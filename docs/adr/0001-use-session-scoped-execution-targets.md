# ADR-0001: Use session-scoped execution targets

## Context and Problem Statement

T3 Code needs a way to run a user's coding work in an isolated remote sandbox, or on an explicitly selected machine, without making that resource another durable T3 environment. The conversation must remain available when a sandbox expires. Selecting compute must not implicitly select a different history owner, provider account, or authorization domain.

**This ADR proposes an execution model; it does not describe an implemented runner or sandbox service.** The existing model keeps execution with the environment that owns the workspace. Direct connections, SSH and T3 Connect change client reachability, not execution ownership, as described in [remote architecture](../internals/remote.md) and the [architecture overview](../internals/overview.md). The following existing paths are useful foundations, but are not sandbox isolation:

- [RemoteDelegation](../../apps/server/src/peer/RemoteDelegation.ts#L189-L357) calls a linked environment's ordinary `t3_thread_launch`, then records a `remoteChild` pointing at the remote-owned thread. Its follower recovers outstanding remote tasks after restart. It explicitly refuses delegated `isolation: "worktree"`, because the two checkouts need not contain the same commit. [Peer links](../internals/remote.md#peer-links) use OAuth MCP; their agents execute as the receiving environment's user. Routing and a `linkOrigin` stamp do not create filesystem isolation.
- The [SSH launcher](../../packages/ssh/src/tunnel.ts#L738-L856) launches `t3 serve` against the remote T3 home and creates an ordinary pairing credential. It distinguishes a launcher-owned server from an already-running external server. This is a full environment with its own state, not an allocation for one coding session.
- The [effect executor](../../apps/server/src/orchestration-v2/EffectWorker.ts#L97-L154) delegates provider starts to `ProviderTurnStartService`; [that service](../../apps/server/src/orchestration-v2/ProviderTurnStartService.ts#L685-L815) resolves policy and opens a provider session for a persisted run and attempt. [Scheduled tasks](../../apps/server/src/scheduledTasks/ScheduledTaskService.ts#L928-L1008) use `ThreadLaunchService` or `ThreadManagementService`, rather than a separate provider-launch path.

The proposed change separates durable environment ownership from execution placement. Existing local environments, independent peers and local/direct/SSH/relay client connections remain valid. Distributed configuration is a separate decision in [ADR-0002](0002-distribute-versioned-cluster-configuration.md): execution targets do not require clustering, and clustering does not require sandboxes or grant permission to use one.

## Decision Drivers

- Keep one authoritative owner for thread history, commands, permissions and execution intent across resource loss and client reconnects.
- Give a coding session a predictable workspace and provider context over multiple runs, with bounded cost and explicit data-retention guarantees.
- Reuse provider adapters and committed orchestration effects without adding network, provisioning or filesystem I/O to the pure Orchestrator.
- Make trust, provider-account placement, cancellation and partition behavior explicit; neither a linked environment nor a cloud allocation is inherently a sandbox.
- Support the same operations from web, desktop, mobile, agents and scheduled tasks, independent of the client's route to its environment.

## Considered Options

- Continue remote-child delegation to an independently owned peer thread.
- Provision an SSH-launched or cloud-hosted full T3 environment for each coding session.
- Keep threads at their home environment and bind coding sessions to lightweight execution runners, including a local implementation.

## Decision Outcome

Chosen option: **"Keep threads at their home environment and bind coding sessions to lightweight execution runners"**, because compute lifetime and trust can then change without changing the owner of the user's conversation. A managed sandbox is an execution resource, never a separately paired environment.

All requirements below are **proposed contracts**. Names identify architectural roles and identity domains, not existing wire fields or service implementations.

### Identity, authority and lifetime

The **home environment** is the existing durable T3 environment that owns the project and thread. It remains the sole writer of authoritative thread projections, history, command receipts, run and attempt identities, execution-session records and retention metadata. A runner reports observations; only home services validate and commit them. No shared SQLite database, replicated thread writer or transparent home failover is assumed.

A user-facing **coding session**, called an **execution session** in the proposed protocol, is one interval of coding work for one home-owned thread, bound to one execution target, workspace lineage and effective configuration snapshot. It starts when home accepts an explicit launch/resume allocation request, including an authorized scheduled launch. It can remain idle between runs. It ends on explicit session close, policy expiry or unrecoverable allocation loss. It is not a browser connection, login, OAuth grant, provider process, or provider-native conversation. The existing [glossary's provider session](../internals/glossary.md#providers-and-checkpoints) retains its meaning; interfaces must qualify these different uses of "session".

| Identity                                           | Owner and lifetime                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EnvironmentId`, `ProjectId`, `ThreadId`           | Existing home identities. The thread outlives every execution session and runner. Remote execution creates no replacement project or thread on the target.                                                                                                                                                        |
| Execution-session ID                               | Allocated and persisted by home. Binds one thread to the selected target, workspace manifest and configuration snapshot. One thread has at most one admitted execution-session writer at a time. A target, workspace-lineage or snapshot change requires a new session after safe release of the previous one.    |
| Execution-target ID                                | A home-local configuration reference to local execution, a managed-sandbox provisioner, a trusted machine, or an explicitly runner-capable peer. It is not an environment ID or a credential.                                                                                                                     |
| Allocation ID and runner binding                   | The provisioner/host identifies the actual resource; home records it. A runner has an authenticated identity and a monotonically increasing home-issued fencing generation for this binding. Transport reconnects do not allocate new compute.                                                                    |
| `RunId`, `RunAttemptId`                            | Existing home-owned units of provider execution and its attempts, bound to an execution session before dispatch. Runs do not own the sandbox's entire lifetime. Retries retain their durable identity or create an explicit new attempt under existing orchestration rules, never an unrecorded second execution. |
| `ProviderSessionId` and native provider references | The existing provider-runtime identities remain distinct. Native references are meaningful only with their provider account, adapter/runtime version, workspace and runner binding; a matching string on another machine proves nothing.                                                                          |

A run can contain multiple native provider turns, notably native goal execution, as documented in [provider constraints](../internals/providers.md#protocol-traps). Ending a native turn therefore does not release the execution session or necessarily end the run. Provider work ending and checkpoint/finalization completing remain separate milestones. Stopping a provider runtime does not delete its thread or, by itself, release the session's workspace.

A runner may contain session-owned subprocesses, terminals and provider subagents. They share the session's authorization ceiling and expiry; creating child work cannot extend either. A separate home-owned child thread requires its own session when it needs independent placement. Existing remote-child delegation remains a different operation: its child belongs to the receiving environment and must not be silently reinterpreted as a runner session.

### Placement and configuration ownership

Home resolves the optional execution target in the shared launch/execution services. Omission means the existing local behavior, not "any available machine." An explicit unavailable target queues within its admitted deadline or fails with a target-specific reason; it never silently runs locally or on another peer. Capacity selection is an offer followed by an authenticated reservation, not proof derived from a cached health indicator. Home owns the queue and reservation intent; the destination owns its capacity, isolation limits and acceptance decision.

The destination atomically reserves its actual slots across all requesting homes, using durable operation identities namespaced by issuing home. Concurrent offers cannot oversubscribe a slot or assign two writers to one workspace, and a reservation retry cannot consume another slot. This is bounded scheduling to an explicit target, not a global scheduler, distributed queue or cluster leader election.

The binding includes an immutable **effective configuration snapshot reference**: issuing home/environment identity, revision, schema version and content digest. It covers resolved execution-affecting defaults and constraints: provider/account bindings, allowed provider/model choices, runtime and interaction ceilings, setup policy, workspace inputs, resource/egress limits and lifetime/retention policy. Before home freezes that reference, destination preflight reports its local bindings, policy and projection versions. Home incorporates the agreed effective values and provenance; a target that cannot satisfy a required value refuses admission rather than silently masking it. The runner receives the validated executable subset, verifies its digest and acknowledges the exact reference before preparing code or starting providers. Unsupported schema or capabilities fail admission. A non-clustered home can issue this snapshot itself; a cluster-distributed revision is resolved into the same effective snapshot under ADR-0002.

Home owns authoritative resolution, overrides and the reference. The runner applies the agreed subset and cannot resolve missing values from ambient T3 settings or substitute its own provider instance with the same ID. Secrets are referenced by binding, not embedded in the snapshot. A changed default or replicated revision affects new sessions only; adopting it requires an explicit safe close/rebind. Current authorization, account revocation, emergency restrictions and lease validity are checked live and can only narrow admission or suspend execution, not silently rewrite the recorded snapshot. They are not frozen grants.

An immutable snapshot does not freeze ordinary run controls. Explicit provider/model or mode changes remain recorded run commands, validated against the pinned allowed choices, actual adapter capabilities and current grants. They use existing provider-switch/context semantics; changing a run selection within that envelope does not require a new allocation. A choice needing another account binding, artifact set or wider policy requires explicit session rebind.

For cluster-sourced profiles, home and runner validate the bounded membership/configuration proof defined in ADR-0002. A valid cached proof avoids a per-session configuration-authority round trip. Expiry or known revocation blocks new cluster-profile admissions, not unrelated standalone or ordinary peer work. Active execution and credential grants still have their own validity and renewal requirements; an immutable snapshot does not preserve expired or revoked authority.

A peer may advertise a runner capability and accept this protocol without accepting ownership of the thread. Its independently durable environment, users, projects and OAuth MCP links remain unchanged. The home needs a separate, explicitly granted execution capability with destination limits; a peer-link token, configuration subscription or cluster membership is insufficient. The peer checks its own permission ceiling, capacity and secret-use grant at reservation and execution. An older peer supporting only ordinary thread launch remains available for remote-child delegation, not selectable as a runner. Runner state on that peer is an allocation journal, not a second authoritative copy of the home thread.

### Execution-target and runner seam

The target adapter provisions, locates and releases resources. The runner operates one session's execution resources. An SSH transport may bootstrap a lightweight runner, but must not call the existing full-server pairing path and relabel the resulting environment a sandbox.

The typed boundary belongs in shared contracts, with capability negotiation for independently versioned homes and runners. It carries home/thread/session/allocation identity, fencing generation, protocol version and operation identity on every applicable message. The minimum semantics are:

| Operation family      | Required semantics                                                                                                                                                                                                                                                                                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Describe and reserve  | Report actual OS/architecture, provider/runtime capabilities, isolation class, credential mechanisms, capacity and expiry enforcement. Reserve only the requested target and snapshot, with a durable idempotency key and deadline. Probing must not run project hooks, create provider sessions or start login flows.                                             |
| Prepare               | Materialize the approved workspace manifest and attachments, establish exclusive workspace ownership, apply setup policy, bind provider credentials and acknowledge readiness with the workspace and snapshot digests. A partially prepared allocation cannot start a run.                                                                                         |
| Execute and control   | Open/resume provider runtime, start a particular run attempt, steer, answer approvals/questions and interrupt through the existing normalized provider semantics. Explicitly report unsupported operations and uncertain delivery. No runner-local scheduler invents subsequent runs or broadens modes. Native goal turns still belong to their home-admitted run. |
| Observe and reconcile | Send ordered, deduplicable provider and resource observations; acknowledge durable ingestion; query operation/process status and replay the runner's unacknowledged journal. Home assigns its own committed event sequence.                                                                                                                                        |
| Workspace access      | Address files, Git/VCS operations, terminal streams, checkpoints, artifacts and optional previews through session-qualified handles, with explicit permissions, bounded transfer and backpressure. An opaque resource handle never grants broader host access.                                                                                                     |
| Renew and release     | Renew a finite lease within the pinned maximum lifetime; stop admission, terminate owned work, export retained state and release the exact allocation. Repeated release is safe. Report cleanup completion separately from the user's accepted close/cancel intent.                                                                                                |

Use the existing [provider adapter](../../packages/provider-core/src/server/ProviderAdapter.ts#L479-L537) and [session-runtime](../../packages/provider-core/src/server/ProviderAdapter.ts#L632-L740) abstractions for provider operations and normalized events, not a new generic shell-command provider protocol. Provider adapters execute where their processes, account profile and workspace reside. Home retains policy checks and authoritative event ingestion; the runner performs target-local adapter I/O. Home-owned text-generation helpers need not move merely because a coding provider moves.

Extend the existing service/effect boundaries: launch services resolve placement; committed outbox effects request allocation, preparation, provider control, checkpointing and cleanup; their service implementations choose local or runner-backed I/O. Runner results enter through guarded commands or event-ingestion services. [EventSink's transaction and outbox boundary](../internals/overview.md#durable-intent-and-side-effects) remains intact. The Orchestrator decides intent from persisted state and performs no provisioning, remote RPC, filesystem work or credential exchange. UI, MCP and schedule handlers remain thin callers of the same services.

### Workspace setup and unpublished work

The home project record remains the logical project association; an absolute home workspace path is not a path on the target. The session binds an explicit workspace manifest containing a verified repository identity, exact base commit/object set, intended branch, transfer digest and setup-policy reference. Repository identity correlates sources; it is not permission to read a clone or proof that two workspaces match.

For remote preparation, a clone URL and branch name alone are insufficient. Home captures a stable input under its workspace coordination boundary. The transfer must include required unpublished commits/objects, index state, tracked working-tree changes and explicitly selected untracked files. Ignored files, credentials and unrelated home directories are excluded unless separately authorized. Missing required submodule/LFS objects, unsupported file semantics, or an uncommitted-only/non-Git workspace without an approved archive representation cause preparation to fail explicitly rather than starting from a nearby clean checkout. Transfers are content-verified, reject path traversal and escaping symlinks, and do not execute imported Git hooks. Clone credentials are scoped separately from any later push permission.

Setup scripts and dependency installation are code execution on the target. They require the pinned policy, allowed network access and credential bindings; inspection or capability probing cannot trigger them. A linked peer's existing policy for remotely originated setup must not be bypassed by choosing runner placement. The provisioner must also establish the isolation it advertises before running setup. A worktree, separate cwd or T3 project record alone is not that isolation.

After readiness the runner workspace is the session's active working copy, including client file edits and terminals. Home does not continuously mirror it into a potentially changing local checkout. Simultaneous sessions cannot write the same workspace lineage; target-side exclusion and home admission both apply. Existing local root/worktree behavior remains valid and is described honestly as local machine execution, not newly sandboxed execution.

Returning work is an explicit, durable export: required Git objects/refs plus index/working-tree/untracked data and selected artifacts, with a verified manifest and recorded base. Downloading or applying it is not a Git push. Applying it to a changed home checkout requires base verification and a visible conflict/merge decision; never overwrite newer local edits. User authorization for execution or clone does not authorize publishing code. Ending a session can preserve an export without applying it to the home checkout.

### Checkpoints, artifacts, files and terminals

The home owns checkpoint identities, attribution, completeness and retention metadata. Capture runs where the active workspace lives. A remote hidden Git ref alone is not a durable home checkpoint: required objects and the capture manifest must reach home-controlled durable storage before the checkpoint is marked available independent of the allocation. Storage may be external, but the session-scoped write capability and authoritative object references belong to home. An ordinary diff or textual summary is not a restorable checkpoint.

[Checkpoint capture](../../apps/server/src/orchestration-v2/CheckpointCaptureService.ts#L63-L139) already distinguishes settled capture retries from new work. Preserve that idempotency and [provider-completion/finalization separation](../internals/overview.md#turn-completion-and-checkpoints). If a provider finishes while export fails, retain its terminal outcome and duration, expose pending/failed finalization, and do not claim a recoverable checkpoint or keep showing live provider work. Revert requires both verified workspace material and the adapter's matching conversation-rollback capability before changing files.

Home remains the client-facing authorization boundary and proxies session resources:

The shared workspace resolver must cover UI and agent/MCP file operations, Git status/diff/branch/commit/push operations, project setup, terminals and checkpoint services. Thread-scoped operations resolve the active execution-session binding, not the home project's original cwd. A project-level operation without a thread/session remains explicitly home-project work; it cannot be silently treated as operating on the runner. Destination paths, credentials and applicable operation grants must agree before I/O.

For a runner-bound thread, a missing, closed or unreachable binding makes live workspace operations unavailable; it never resolves them back to home's checkout. Historical checkpoints and artifacts remain addressable by their retained session-qualified references. Returning to local execution is an explicit verified rebind, not a filesystem fallback.

- Provider input attachments remain home-owned records. The runner receives only explicitly claimed content through expiring object-scoped transfer grants; home paths are not embedded as usable runner paths.
- Files and artifact handles identify the execution session/allocation as well as their paths or objects. Runner reads and writes enforce canonical target paths and session policy. Do not interpret a remote absolute path on home, or automatically give a remote agent home-wide filesystem access. Existing [home filesystem permissions](../internals/environment-auth.md#the-environment-is-the-filesystem-boundary) remain unchanged for local operations.
- Terminals run with the session's target cwd, account boundary and lease, rather than the home terminal manager accidentally spawning at a same-looking path. Namespace terminal IDs by binding; reconnect can resume bounded output only for a still-live PTY, and must not fake PTY survival after resource loss. Terminal input retains its separate shell-operation permission.
- Preview/port forwarding is an explicitly granted, session-scoped service route, not an unrestricted network proxy. Signed download/preview capabilities have short expiries; revoking their issuer does not retract bytes already downloaded or an already-issued bearer URL before its expiry.

Home persists user-visible history, attachment/artifact references and retained projections using existing retention rules. The [event log is pruned](../internals/overview.md#durable-intent-and-side-effects); it cannot reconstruct the entire home database or all historical provider output. Runner journals are delivery buffers, not a replacement history store. A missing journal range is a visible reconciliation failure, not permission to invent events or infer a complete workspace.

### Provider capability placement and credential isolation

Admission uses the actual target's executable/runtime versions, provider account availability, model catalog, permission enforcement, background-work behavior, native resume, checkpoint and conversation-rollback capabilities. A provider available at home is not thereby available on a target. Map the selected home provider instance to an explicitly authorized target account binding; equal instance IDs across peers imply no account relationship. The effective operation set is the intersection of the caller's grant and modes, home's policy, the pinned snapshot, the destination's policy and the actual adapter capabilities.

The runner uses a dedicated per-session account/profile directory and allowlisted process environment. Do not copy the user's home directory, ambient CLI/keychain stores, browser auth, T3 database, signing key, peer tokens, SSH agent or cloud provisioning credentials into a sandbox. Provider mechanisms must support an approved session-scoped credential or a deliberately granted target-resident account; otherwise the combination is unsupported. A portable conversation summary is not an authentication or native-session export mechanism. Shared provider helpers may be reused only where the adapter can prove profile, MCP-entry and approval isolation across sessions; otherwise isolate them per session.

Credential purposes remain separate:

- Home-held cloud/host management credentials allocate and terminate resources. They are never delivered to provider processes.
- Runner-control credentials have a dedicated audience, authenticated target identity and scope limited to the home/thread/execution-session/allocation/generation. Use authenticated encrypted transport and bind enrollment to an approved host/provisioner identity, not a self-reported environment ID or an arbitrary endpoint.
- Provider/forge/MCP credentials are individually scoped to account, repository, operation, session and expiry as supported. Provider-originated T3 tool callbacks authenticate to home with the correct thread/run and mode ceiling, not an administrative home pairing token. Remote filesystem tools resolve the runner workspace; unrelated home or peer capabilities require their own explicit grants.
- Export recovery can use a separately authorized, read/export-only grant after execution is disabled. It cannot retain permission to start processes or renew the execution lease.

Revocation immediately closes home admission, callback access, lease renewal and broker-issued secret access; home requests target termination and revokes upstream credentials where supported. A disconnected runner enforces its already-issued lease and credential deadlines locally. **Immediate remote termination during a network partition is not guaranteed.** Long-lived target-resident accounts cannot be made session-revocable merely by removing a T3 reference; their residual authority must be disclosed and require explicit trust. A hostile runner may retain secrets or execute outside software fences. Strong sandbox claims require enforceable OS/VM isolation, bounded egress, managed credentials and an independently enforceable resource TTL; a trusted user's machine or full-access peer must not claim those guarantees without providing them.

### Lifecycle, failure and fencing

Home persists session transitions through **requested → provisioning → preparing → ready → draining → closed**; irrecoverable resource loss records **lost**. A ready session can execute multiple runs or sit idle. Queueing, provider execution and connectivity are separate states, not misleading replacements for run state. Rejection or failure before readiness records the failed stage/reason and enters draining/cleanup without starting a provider. Closed/lost records survive allocation deletion and may retain **cleanup pending** or **export incomplete** evidence.

The admitted snapshot fixes finite allocation/prepare deadlines, idle timeout, maximum session lifetime, execution lease duration and export-retention deadline. Home owns these policies; the runner/provisioner must enforce the limits it accepts. Lease renewals do not extend the maximum lifetime. A session may remain idle only while its allocation is retained and authorized. An idle timeout closes it; later work needs a new, explicitly prepared session. Neither an open client tab nor an unrelated provider process grants an infinite lease.

Provisioning is intent-first: persist the session and stable allocation key before calling the provisioner, then reconcile by that key after a lost response. A provisioner must support idempotent create or reliable lookup/adoption of the exact tagged resource. If it cannot distinguish an uncertain create, block and reconcile rather than allocate a second billable resource. The management plane keeps cleanup ownership even if the runner never registers. It must never terminate an externally owned server or unrelated machine resources.

Every mutating runner operation has a durable idempotency identity scoped to home, session, run/attempt where relevant, and operation. Reuse with different content is a conflict. Runner acceptance and execution status are journaled; home outbox retries query/reconcile that status before sending again. Process launch can fail between journal and spawn bookkeeping: an uncertain provider start is reconciled against the owned process/native conversation, not blindly replayed. This is not an exactly-once guarantee for arbitrary provider tool effects or external Git/API actions.

The binding's fencing generation is checked at runner admission, home observation ingestion, artifact publication and callbacks. A stale connection cannot start new work, attach an old approval, publish a current checkpoint or overwrite a newer workspace export. Generation fencing alone cannot stop an old process's external side effects. Before admitting a replacement writer, home requires confirmed termination or enforceable lease expiry/host fencing, and proof that workspace exclusion has been released. A target lacking such proof stays blocked; creating a new generation is not proof that the old process stopped.

Failure handling follows the ownership boundary:

- **Client disconnect:** home and runner continue authorized work within the lease. Reconnecting web, desktop or mobile reads home state; it does not provision again.
- **Home–runner partition:** no new operations are admitted across the break. The runner may finish already-admitted work only within its existing lease, journals observations, and cannot obtain new approvals or credentials. A bounded journal applies backpressure; exhaustion stops/pauses work through supported provider control rather than silently discarding history. Lease expiry terminates owned provider/subagent/terminal work and blocks further writes. Home reports reachability and stop uncertainty, attempts management-plane termination where possible, and never schedules a duplicate elsewhere merely because heartbeats disappeared.
- **Home restart:** recover retained projections, receipts and outbox intent, then reconcile the recorded allocation, generation and acknowledged observation cursor. Renew only a still-authorized session. Do not infer from an incomplete event replay that an operation never ran, and do not replay provider-start effects until their remote status is known.
- **Runner restart:** re-authenticate and reconcile the same allocation's journal, workspace digest/ownership and native provider state. Resume only an explicitly supported, verified adapter path. A binding replacement advances the generation after fencing the old writer; a reconnect to the same live binding does not. If the resource, journal or native state is missing or another process owns the conversation, report loss/blocked recovery rather than transparently creating fresh context.
- **Cancel/Stop:** commit intent at home with its normal receipt. Cancelling a queued run prevents dispatch. Stopping admitted work interrupts the identified run and its owned native goal/background/subagent work; it does not necessarily release an otherwise valid idle session. Ending the execution session closes admission, cancels its pending runs, interrupts its owned processes/terminals, attempts a consistent partial-work export, revokes execution grants and releases its allocation. A user-visible accepted cancellation is not a claim that an unreachable process has stopped; stop confirmation and cleanup remain visible and retryable.
- **Expiry or cleanup failure:** the runner/host enforces process and lease expiry independently of home connectivity, and the provisioner enforces managed-resource TTL. Home retries idempotent release by allocation identity until deletion is confirmed. Cleanup removes session-owned credential material and writable resources, not shared machine installations or unrelated peer state. Residual cleanup failures remain recorded; they are not hidden by marking the run terminal.

Before normal destruction, a verified export must reach durable storage or the user must explicitly discard the remaining work. A graceful close retains/quarantines owned storage for recovery until the pinned retention deadline when export fails; execution stays disabled. Hard infrastructure TTL, destructive host loss or a security-required termination can still destroy work newer than the last durable export. Show that boundary and last durable checkpoint rather than promising zero loss. Retention deletion applies only to the owned allocation/export after its published deadline; it is never a blanket delete of the project's original checkout.

There is **no automatic migration or live handoff** between targets. At a safe stopped boundary, explicit continuation may create a new session only after verifying workspace export/import completeness and the destination adapter's actual resume or handoff capability. [Portable handoffs](../internals/context-handoffs.md) omit native context, tool/approval state and some text; they cannot establish native parity. If native resume is unavailable, an explicitly accepted fresh-provider-context continuation may use a summary and the verified workspace, with that loss disclosed. Existing local fallback behavior is not evidence that cross-machine resume is safe.

### Surface coverage and compatibility

Web (hosted and locally served), desktop and mobile connect to **home**, select or display its execution target, and use its existing authorization and subscriptions. They do not pair to managed runners, substitute their own filesystem/provider credentials, or expose a second environment merely to reach a terminal. Desktop may offer SSH bootstrap integration but is not required to stay open to supervise a session. A home that is itself desktop-hosted must renew leases while running; if that home sleeps, partition/expiry policy applies honestly.

Selection, launch/resume, target status, queueing, Stop, session close, resource forwarding and export recovery must be shared service capabilities. Agent MCP tools and scheduled tasks use the same admission path and mode ceilings. A schedule records an authorized target policy; each firing revalidates execution and secret grants, and a new session also revalidates capacity and current allowed configuration. Agents cannot redirect a session, request secrets or schedule higher-privilege future work by supplying a target ID.

A task reusing one thread may reuse its still-ready execution session and workspace between firings, subject to the pinned idle/maximum lifetime. The existing [fresh-session destination](../user/project-settings.md#scheduled-tasks-on-mobile) changes provider context only: it does not by itself discard the workspace, allocate compute or change the execution-session ID. If the execution session has expired, the schedule needs an explicit policy authorizing a new session and a verified workspace continuation from the last durable export; it cannot quietly start from a clean clone. Native provider context may be fresh or resumed according to that task's separate setting and actual adapter capability. Existing bindings keep their pinned configuration until explicitly replaced.

Local, LAN/direct, SSH-forwarded and T3 Connect/relay routes to home remain transport choices. Runner connectivity is a separate authenticated home-to-target channel; no browser loopback assumption or relay login substitutes for runner authorization. Feature availability follows advertised home and runner capabilities, not the installed client's version. Older clients keep valid local/peer workflows; they may control a runner-backed thread through compatible existing commands only when home can enforce the binding and return decodable state. Otherwise the feature requires an explicit compatible client rather than ambiguous target-changing behavior.

### Migration strategy

This proposed ADR changes no runtime behavior. Implementation begins by introducing the typed placement/session contracts and a local execution-target implementation behind the existing launch, provider, checkpoint and cleanup services. Local remains the default; existing thread/run/provider identities and historical records are not rewritten into sandbox allocations. Stored-event and client protocol compatibility must be addressed before new session records or events can be persisted on an environment.

Remote admission is enabled only for destinations that negotiate the complete required preparation, control, forwarding, reconciliation, fencing and cleanup capabilities. Unsupported providers or credential mechanisms remain explicitly unsupported on that target; do not fall back to another account or machine. Provisioner integrations reuse the same runner contract instead of adding cloud-specific branches to Orchestrator or clients. The initial deployment must retain the current independent peer-delegation and SSH-full-environment paths alongside the distinctly named execution-target path.

Existing threads on independent peers stay there. They are not imported, reparented or deleted as an adoption side effect. Opting a stopped home thread into remote execution creates a new session from a verified workspace capture; moving back follows the same explicit export and context-continuation rules. Once a path adopts the runner boundary, migrate all of that path's callers to the shared service and remove obsolete bypasses, rather than maintain a second scheduler. Clustering can supply configuration revisions later without changing execution authority or requiring thread/database migration.

### Consequences

- **Positive:** sandbox loss does not delete or move the authoritative thread, and independently owned environments remain independently owned.
- **Positive:** local machines, managed sandboxes and explicitly capable peers share placement and lifecycle semantics without assuming they offer equal isolation.
- **Positive:** one service boundary supports interactive, agent-driven and unattended work; policy and cancellation cannot diverge by surface or transport.
- **Negative:** home availability is required for admission, approvals and lease renewal. A partition or sleeping home can interrupt useful remote work even while compute is healthy; this deliberately favors bounded authority over automatic availability.
- **Negative:** remote workspace transfer, durable checkpoint exports, journals and home-mediated forwarding add latency, bandwidth, storage cost and protocol/versioning obligations. Unpublished work is materially harder than cloning a branch.
- **Negative:** adapters and provisioners must prove resume, account isolation, expiry and uncertain-operation reconciliation. Some providers/hosts will be unusable for remote sessions, and trusted-machine execution cannot offer managed-sandbox guarantees.
- **Negative:** work beyond the last durable export can be lost at hard resource expiry or destruction. There is no transparent failover or native-context equivalence to hide that risk.
- **Neutral:** an execution session is a new explicit domain lifetime; it does not replace provider sessions, auth sessions, durable threads or independently paired environments.

## Pros and Cons of the Options

### Continue remote-child delegation

- Good, because the OAuth MCP link, remote thread ownership and task follower already exist, and the receiving environment manages its own providers and long-lived workspace.
- Good, because it remains the right choice when the user actually wants another independently durable environment to own the work.
- Bad, because the parent's task references a different environment's ordinary thread; resource expiry, credentials and history ownership cannot be treated as the lifetime of one home coding session.
- Bad, because execution as the receiving user is routing, not sandbox isolation, and repository correlation does not transfer unpublished workspace state.

### Provision a full T3 environment per coding session

- Good, because existing server, pairing, provider, terminal and file features can operate with few new execution-specific abstractions.
- Good, because an intentionally long-lived remote environment has an understandable standalone management boundary.
- Bad, because a temporary allocation gains its own environment identity, database, settings, OAuth/pairing state and conversation ownership. Keeping the conversation after expiry then requires another ownership-transfer design.
- Bad, because provisioning/admin credentials and environment-wide APIs are a larger trust and cleanup surface than a session runner, and SSH process ownership is not isolation.

### Bind home coding sessions to lightweight runners

- Good, because durable authority is separated from resource lifetime and target placement is explicit without moving the thread.
- Good, because existing normalized provider and orchestration-effect seams can be extended for local and remote execution rather than replaced with transport-specific schedulers.
- Bad, because resource reconciliation, workspace exports, scoped credential delegation and forwarding need a new, independently versioned protocol with real operational guarantees.
- Bad, because bounded leases trade availability for safety, provider portability is limited, and deletion/export failures remain user-visible rather than being concealed by automatic handoff.

## More Information

### Acceptance scenarios

These scenarios would establish an implementation's conformance; they are not claims of verification performed for this proposal.

1. **Durable ownership:** launch one home thread on a managed target, execute multiple runs including a provider-native goal with multiple native turns, and close the session. All runs remain under the original home `ThreadId`; the target never creates a paired environment or an ordinary remote-owned child thread. A later explicitly prepared session reuses the thread, not the expired allocation.
2. **Every surface and route:** web, desktop, mobile, an authorized MCP agent and an unattended scheduled task exercise the same target admission and Stop/close services. Reconnecting a client over direct or relay transport neither allocates compute nor changes target. A plan-mode/read-only caller cannot obtain higher execution or shell access through any of these paths.
3. **Existing environments stay valid:** ordinary local execution, saved direct/SSH/relay environments and existing remote-child tasks keep their ownership and restart behavior. A linked peer without runner capability refuses runner scheduling but can still accept its existing authorized thread-launch calls. A capable peer accepts a home-owned session only with an explicit execution grant.
4. **Exact workspace inputs:** prepare from an unpublished commit, staged and unstaged edits, and selected untracked files. Digests and resulting contents match; missing LFS/submodule data and escaping paths fail before setup/provider launch. Export back to a changed home checkout produces a conflict rather than overwriting it, and no push occurs without a separate publishing authorization.
5. **Capability and account placement:** a provider installed only at home cannot be silently used on a target. Two sessions using the same driver do not share account profiles, MCP entries, ambient credentials or approval grants. An unsupported credential-delegation mechanism fails admission; probing runs no hooks or login flow. Full-access trusted-machine execution is not labeled an isolated sandbox.
6. **Pinned configuration without implicit trust:** a runner verifies the exact effective snapshot reference and rejects mismatches. A later cluster/default update does not alter an active session. Removing execution/secret permission immediately stops home admission, callbacks and renewal, while a partitioned runner is bounded by its existing lease/credential expiry. Cluster membership alone cannot reserve or read session secrets.
7. **Uncertain provisioning and duplicate delivery:** lose a create response and restart home before recording readiness. Reconciliation finds the same tagged allocation, charges for no duplicate resource, and can clean it up without runner registration. Two homes racing for one destination slot cannot both reserve it or collide through equal client-generated keys. Repeated start/control/export/release requests return the recorded result; same key with changed content conflicts. An uncertain provider spawn blocks until reconciled instead of repeating a potentially executed prompt.
8. **Partition and fencing:** disconnect home from an executing runner, then attempt to admit work elsewhere. Home refuses duplicate execution until old-writer termination or enforceable expiry is proven. The old runner stops owned work at its lease deadline; stale-generation events, approvals, file writes and checkpoint publication cannot mutate the new binding. If termination is unconfirmed, the UI says so rather than claiming immediate remote cancellation.
9. **Restart without invented history:** restart home after event-log pruning while a runner has acknowledged and unacknowledged observations. Retained projections/receipts plus the recorded cursor and journal reconcile without duplicate provider starts. A missing journal range is reported as incomplete recovery; it is not reconstructed by assuming the full historical event log exists.
10. **Provider-safe restart and continuation:** restart the runner with the workspace present. Only an adapter-proven native resume continues its conversation; a native conversation owned elsewhere blocks. Destroy the allocation or change the target and require explicit verified workspace transfer and supported context continuation. A summary-only continuation clearly starts fresh provider context, with no automatic live migration or claim of native/tool/approval parity.
11. **Completion and durable recovery:** finish provider work while checkpoint upload is unavailable. Home records provider completion without extending its duration, shows incomplete finalization and does not mark a remote-only ref durably available. After verified objects/manifests are stored, deleting the allocation leaves the declared checkpoint, artifacts and thread history readable; unsupported conversation rollback refuses before filesystem changes.
12. **Cancel, expiry and cleanup:** cancel a queued run before dispatch; Stop an active native goal and its owned background work; separately end the session while the runner is unreachable. Intent receipts are idempotent, stop uncertainty/cleanup remain visible, lease expiry disables execution, and management cleanup eventually releases only owned resources. Failed export retains recoverable storage until its declared deadline when possible; hard TTL loss is reported against the last durable export.
13. **Resource-forwarding boundary:** terminal/file/preview operations from all clients address the runner session, never same-looking home paths. Revoked or stale handles and traversal/symlink escapes fail, a recreated PTY is not presented as the old live terminal, and an artifact-only recovery grant cannot start a process. A previously issued bearer download expires according to its explicit lifetime rather than a false immediate-revocation promise.
